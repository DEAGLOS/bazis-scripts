# Формат `.ldw` / `.bln` (Базис-Мебельщик) — техническая спецификация

Неофициальный формат, восстановлен реверс-инжинирингом (побайтовые
диффы пар файлов с одним контролируемым отличием), у Базис-Центра
документации на него нет. Часть полей помечена как **неразгадано** —
это либо неиспользуемые/служебные данные (не влияют на отображение),
либо просто ещё не проверенные гипотезы. Все смещения — от начала
СВОЕЙ записи, если не указано иное. Все целые и `double` — little-endian.

## 0. Общее

- Кодировка текста — **CP1251**.
- Строки — Pascal ShortString: 1 байт длины + N байт текста (без
  завершающего нуля).
- Координаты — `double` (8 байт), в миллиметрах.
- Формат исторически предшествует `.b3d` (3D-формат того же
  производителя) — многие механизмы узнаваемы в обоих (дискриминатор
  типа после тега, центр+2 точки у дуги и т.п.), но раскладка полей не
  идентична.

## 1. Контейнер `.bln` (библиотека)

`.bln` — обычный **OLE Compound File** (Composite Document / CFBF —
тот же контейнер, что у старых `.doc`/`.xls`/`.msi`), без сжатия.
Стандартный формат, готовые библиотеки есть под любой язык (Python:
`olefile`; JS: пакет `cfb`; .NET: `System.IO.Packaging`/`OpenMcdf` и т.п.)
— свой парсер контейнера писать не нужно.

Внутри — плоский набор потоков в корне контейнера:

- **`$$Lib_structure$$`** — служебный поток, XML-оглавление,
  **UTF-8 с BOM**:

  ```xml
  <?xml version="1.0" encoding="UTF-8"?>
  <FileSystem>
    <FilesCount>6</FilesCount>
    <Version>81</Version>
    <Directory>
      <Name>Название папки</Name>
      <File>
        <Name>Отображаемое имя чертежа.ldw</Name>
        <Storage>File1.ldw</Storage>
      </File>
      <!-- ...ещё File, вложенные Directory... -->
    </Directory>
    <!-- File может быть и прямо на верхнем уровне, без Directory -->
  </FileSystem>
  ```

  `<Directory>` может быть вложен произвольно глубоко. `<File><Name>`
  — то имя, что видит пользователь; `<Storage>` — имя ПОТОКА внутри
  контейнера, где реально лежат байты.

  ⚠️ `<FilesCount>` может не совпадать с реальным числом `<File>`-
  записей (встречалась библиотека с заявленными 6 файлами и только 5
  тегами `<File>`, с пропуском в нумерации `Storage`, вероятно от
  когда-то удалённого файла) — **не полагаться на `<FilesCount>`,
  просто перечислять реальные `<File>` теги.**

- **`FileN.ldw`** (`File1.ldw`, `File2.ldw`, ...) — сами документы,
  **плоско в корне** контейнера независимо от вложенности папок в XML.
  Имя потока — техническое, генерируется Базисом, не связано с
  отображаемым именем. Содержимое каждого потока — **байт-в-байт
  обычный `.ldw`-файл** (см. ниже), тот же формат, что и при сохранении
  чертежа отдельным файлом вне библиотеки.

## 2. Файл/поток `.ldw`

### 2.1 Заголовок

| Смещение | Тип | Значение |
|---|---|---|
| 0 | байт | `0x0B` — длина следующей Pascal-строки (11) |
| 1-11 | ASCII | `*BAZIS*LDW*` — сигнатура |
| 12-15 | 4 байта | `00 00 00 00` — паддинг |

Итого фиксированный заголовок — 16 байт (`0x10`).

### 2.2 "Указатели" в начале файла (0x10–0x50)

Несколько переменных int64/double-полей в этом диапазоне выглядят как
живые указатели памяти Delphi-процесса на момент сохранения (значения
не коррелируют с размером/содержимым файла) — **игнорировать при
парсинге**, значимых данных не несут.

### 2.3 Шаблон "пустой чертёж"

Каждый новый чертёж (даже совсем пустой) содержит константный блок
~2.4КБ (до смещения `0x98A`) с двумя дефолтными "Видами" (`Вид0`,
`Вид1`), у каждого свой `Слой1`. Внутренняя раскладка полей Вида/Слоя
(кроме масштаба, см. §4) не разобрана — не требуется для отображения.

**"Виды" в этом парсере не разделяются** — вся геометрия читается как
один общий плоский список примитивов, без привязки к конкретному Виду
(см. §4 про исключение — масштаб всё же учитывается).

### 2.4 Общий заголовок геометрических записей

LINE (0x01), ARC (0x03) и CIRCLE (0x02) используют общую "шапку":

| Смещение | Тип | Значение |
|---|---|---|
| 0-1 | int16 | тег: `1`=линия, `3`=дуга, `2`=окружность |
| 2-5 | int32 | для LINE/ARC — длина хвоста записи; для CIRCLE/блока/размера-обёртки — **тип объекта, не длина** (см. §2.7) — определять эмпирически для новых тегов, не считать длиной по умолчанию |
| 6 | байт | тип линии (`style`, см. §3) — для CIRCLE это же смещение = `1` |
| 7 | байт | 0 либо флаг типа указателя размера (см. §5) |
| 8 | байт | обычно 0; у ГЛАВНОЙ линии размера — тип указателя (стрелка и т.п., см. §5) |
| 9 | байт | 0 |
| 10 | байт | как байт 8 (дублируется, оба меняются синхронно) |
| 11 | байт | 0 |
| 12-19 | double | константа `-1.0` (у style=0 — вспомогательная линия — здесь `0.0`); смысл не разгадан |
| 20 | байт | R цвета |
| 21 | байт | G цвета |
| 22 | байт | B цвета |
| 23 | байт | не разобран (всегда 0 в тестах) |
| 24 | байт | флаг "цвет явно переопределён пользователем" (`1`=да) |

Толщина линии отдельного поля не имеет — предположительно "зашита" в
конкретный номер типа линии (см. §3).

### 2.5 LINE — тег `0x01`

После общего заголовка (25 байт) — координаты, весь размер записи 57
байт:

| Смещение | Тип | Значение |
|---|---|---|
| 25-32 | double | X1 |
| 33-40 | double | Y1 |
| 41-48 | double | X2 |
| 49-56 | double | Y2 |

### 2.6 ARC — тег `0x03`

После общего заголовка — 1 байт-флаг (назначение не разгадано,
возможно направление обхода) + 3 точки, весь размер записи 74 байта:

| Смещение | Тип | Значение |
|---|---|---|
| 25 | байт | флаг (не разгадан) |
| 26-33 | double | X точки A (конец дуги) |
| 34-41 | double | Y точки A |
| 42-49 | double | X точки B (конец дуги) |
| 50-57 | double | Y точки B |
| 58-65 | double | X центра |
| 66-73 | double | Y центра |

Направление, в котором рисуется дуга между A и B (какая из двух
половин окружности), не разгадано — при отрисовке нужно выбирать
эвристикой или считать всегда "короткую" дугу.

### 2.7 CIRCLE — тег `0x02`

Фиксированная длина 45 байт, без строк:

| Смещение | Тип | Значение |
|---|---|---|
| 0-1 | int16 | `0x0002` |
| 2-5 | int32 | `48` — тип объекта (НЕ длина записи) |
| 6 | байт | `1` (аналог style) |
| 7 | байт | `0` (паддинг) |
| 8-15 | double | `-1.0` (та же константа) |
| 16-20 | 5 байт | `00 00 00 00 01` — не проверено на цветной окружности |
| 21-28 | double | X центра |
| 29-36 | double | Y центра |
| 37-44 | double | радиус (не диаметр) |

Цвет/стиль окружности не тестировался отдельно — вероятно, та же схема
RGB+флаг, что у LINE, смещения не подтверждены.

### 2.8 Текст / автоподпись размера — тег `0x19` (25)

```
[tag: int16 = 0x0019]
[int32 declared_len]        — длина payload'а ДО и ВКЛЮЧАЯ int32 fontlen,
                               НЕ включая сами байты имени шрифта
[int32 color]                — упакованный RGB: R | G<<8 | B<<16
[byte overrideFlag]          — 1 = цвет НЕ переопределён (не 100% подтверждено)
[byte subtype]                — 0x0B=произвольный текст
                                 0x05=автоподпись размера, дробное значение
                                 0x03=автоподпись размера, округлённое целое
[12 байт нулей]
[double param1]               — текст: кегль шрифта (мм)
                                 размер: смысл не до конца ясен (в тестах 5.0)
[double const1 = 1.0]         — константа, смысл не ясен
[double X1][double Y1]        — точка привязки 1
[double X2][double Y2]        — точка привязки 2 (угол X1Y1→X2Y2 = поворот текста)
[double width]                 — кэш X2−X1, не самостоятельное значение
[int32 strlen][strlen байт]    — сама строка (текст — UTF-8; число размера —
                                  ASCII, десятичный разделитель ",")
[byte 0x00]                    — разделитель
[int32 fontlen][fontlen байт]  — имя шрифта (ASCII), fontlen=0 если не задан
```

Кегль текста (`param1`) — **не масштабируется масштабом Вида ни для
одного подтипа**, только позиция (X1,Y1,X2,Y2) масштабируется.

Геометрия наконечников (стрелок) размера отдельно НЕ хранится —
рабочая гипотеза: рисуются на лету по направлению линии, аналогично
`Size3D` в 3D-формате `.b3d`.

**`declared_len` встречается и как `96`, а не только `104`** —
подтверждено на реальной старой библиотеке `.bln`. Раскладка полей ДО
`int32 strlen` (включительно, вместе с самой строкой) идентична
байт-в-байт для обоих значений; разница в 8 байт — где-то в
необязательном хвосте после строки (имя шрифта и что вокруг него), на
сам текст не влияет. Парсер должен принимать оба значения как валидную
длину записи текста.

### 2.9 Обёртка объекта "Размер" — тег `0x1D` (29)

Ровно 820 байт перед геометрией размера (`3×LINE + 1×TXT19` — 2
плечевые линии + 1 главная измерительная линия + подпись). Содержимое
— редакционные метаданные (связи между размерами: общая база / цепь и
т.п.), **на отображение не влияет** — при парсинге достаточно
пропустить 820 байт и читать дальше как обычно (LINE/ARC/0x19).

Количество тегов `0x1D` в файле = количеству объектов "Размер".

### 2.10 Обёртка блока/группы — тег `0x73` (115)

```
[tag 0x73][int32 blockKind][ShortString имя блока]
...
[ShortString "Слой1"]   — свой вложенный слой блока
...
[дочерние LINE/ARC/... — геометрия блока]
```

`blockKind` — дискриминатор способа создания (например `6` для фигуры,
построенной инструментом "Многоугольник", `3` для линий, объединённых
вручную через выделение+группировку) — полный список значений не
составлен. Полная раскладка полей между именем блока и `Слой1`, и
между `Слой1` и первой геометрией — не разобрана; для отображения
можно игнорировать иерархию и просто продолжать читать примитивы
последовательно.

### 2.11 Штриховка — тег `0x06`

```
[tag: int16 = 0x0006]
[int32 type = 4]
[byte = 1][byte = 0]
[double spacing]          — шаг штриховки, мм
[byte R][byte G][byte B]  — цвет линий штриховки
[byte — не разобран]
[byte angleDeg]           — угол штриховки в градусах
```

Сразу за заголовком — контур: **замкнутая цепочка LINE-записей по
связности** (конец одной = начало следующей, до возврата в исходную
точку). Стиль линий контура может быть любым (видимая линия реза,
обычная геометрия детали, или невидимая служебная — `style=10`) —
**фильтровать по стилю нельзя**, собирать контур строго по
геометрической связности координат.

## 3. Тип линии (`style`, байт 6 общего заголовка)

| `style` | Вид |
|---|---|
| `0` | вспомогательная (бесконечная) линия — см. §3.1 |
| `1` | сплошная тонкая |
| `2` | пунктирная, мелкий частый штрих; также используется как служебный стиль плечевых/измерительных линий размера |
| `3` | пунктирная, штрих крупнее/реже |
| `4` | штрихпунктирная тонкая |
| `5` | штрихпунктирная жирная |
| `6` | волнистая (значок "обрыва" в черчении) |
| `7` | частый мелкий штрих |
| `8` | сплошная жирная |
| `9` | тонкая с одной отметкой-изломом посередине |
| `10` | невидимая (координаты есть, не рисуется) |

Толщина отдельного поля не имеет, вероятно "зашита" в номер типа (`5`
и `8` — жирные варианты `4` и `1`).

### 3.1 Вспомогательная (бесконечная) линия

`style=0` вместе с константой на смещении +12 = `0.0` (не `-1.0`).
Координаты строго симметричны относительно `(0,0)`
(`X2=-X1, Y2=-Y1`) — "бесконечность" реализована огромным отрезком
через мировой ноль в заданном направлении, не отдельным примитивом.
Обычно системного зелёного цвета `(0,255,0)`. Рекомендуется полностью
игнорировать при отображении (не рисовать, не учитывать в габаритах).

## 4. Цвет

Простой RGB-триплет на смещениях +20/+21/+22 общего заголовка (см.
§2.4), НЕ индекс палитры. Байт +24 — флаг "цвет явно выбран
пользователем" (не то же самое, что "RGB ненулевой" — у системных
цветов по умолчанию флаг может быть не установлен при ненулевом RGB).

## 5. Тип указателя размера

Байты +8/+10 общего заголовка ГЛАВНОЙ (измерительной) LINE-записи
объекта "Размер" (у плечевых/выносных линий того же размера — всегда
0):

| Значение | Смысл |
|---|---|
| `0x00` | нет указателя (плечевые/выносные линии) |
| `0x01` | стрелка |
| `0x03` | альтернативный тип из списка Базиса — визуально не подтверждён (возможно другой вид стрелки, засечка или кружок — в UI Базиса минимум 4 варианта) |
| `0x04` | линия-выноска на позицию детали (отдельный от размера механизм, не измерение) |

## 6. Масштаб вида

Каждый "Вид" может иметь собственный масштаб отображения. Поле —
`double`, лежит **ровно за 293 байта до метки своего Вида** (строка
`"ВидN"` в файле). Есть отдельно похожее поле на смещении `0xCE` от
начала файла — это масштаб "последнего активного на момент сохранения"
Вида (глобальный UI-индикатор), не то же самое, что per-view поле.

**Масштаб НЕ влияет на исходные координаты примитивов** (они хранятся
"как нарисовано", без домножения). При отображении многовидового
чертежа единым листом масштаб нужно применять постфактум:
`координата_на_экране = координата_из_файла × масштаб_своего_Вида`,
считая **от мирового нуля `(0,0)`**, не от центра содержимого Вида.

Кегль текста (`param1` в §2.8) на масштаб Вида **не домножается ни при
каких условиях** — только позиция текста.

⚠️ Даже "обычные", не специально масштабированные Виды (в т.ч. оба
дефолтных `Вид0`/`Вид1`, которые есть в КАЖДОМ файле) могут нести
не-`1.0` значение в этом поле на реальных файлах — оно не является
надёжным индикатором "пользователь специально изменил масштаб".

## 7. Что осознанно не реализовано / не разгадано

- Привязка примитивов к конкретному "Виду" (в каком Виде что находится)
  — сами Виды не разделяются, всё рисуется одним общим плоским листом;
  при наложении контента разных Видов в одном диапазоне координат
  возможно визуальное наложение (осознанное упрощение).
- Полная раскладка полей Вида/Слоя (кроме масштаба), обёртки блока
  (`0x73`) и обёртки размера (`0x1D`) — содержат редакционные
  метаданные, не влияющие на отображение, разбирать не требовалось.
- Точный визуальный вид типов указателя размера `0x03` и выше (список
  Базиса содержит минимум 4 варианта — без указателя/стрелка/
  засечка/кружок).
- Назначение константы `-1.0`/`0.0` (общий заголовок, смещение +12) и
  нескольких служебных байт-полей, которые во всех виденных примерах
  были нулевыми (толщина линии как отдельное поле, если она вообще
  существует отдельно от номера типа).
- Направление обхода дуги (какая из двух половин окружности между
  точками A и B).
