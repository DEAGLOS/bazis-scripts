# Материалы и текстуры

Читать вместе с `../CLAUDE.md` и `geometry.md` (структурные уроки про
локальные оси).

## Приоритеты источника цвета/текстуры панели (подтверждено практикой)
1. `TexturePath` → basename → карта загруженных текстур.
2. Фолбэк — `.dae` по имени (без `\r`-артикула).
3. `DiffuseColor` — НЕ всегда честный (тест: #535353 серый в JSON, панель
   в Базисе чёрная). `Obj.Material` — только 4 поля, глянец/прозрачность/
   точный цвет некоторых декоров живут в базе материалов Базиса, скрипту
   не пробрасываются (`.dae` тоже не спасает — дефолт-заглушки).
   `PanelPlastic` (накладка) — вообще без цвета/пути.

**Решение**: ручная классификация через диалог экспортёра (см. ниже) +
`MaterialColorFallback` ВСЕГДА побеждает `DiffuseColor` для панелей без
текстуры.

## material_config.js (рядом с вьювером, правит пользователь вручную)
`MATERIAL_TYPES` — 9 типов: `face{roughness,metalness,opacity,
transparent,mirror}` + `edge{mode,...}`. `mirror:true` → рендерится через
`THREE.Reflector` (см. `ui.md`). `edge.mode`: `"face"`/`"color"`/
`"texture"`/`"noise"`.
`MATERIAL_KEYWORDS` — фолбэк-эвристика по имени материала
(`USE_NAME_PARSING_FALLBACK`).
ДСП/ЛДСП дефолт: `edge:{mode:"noise", color1:"#d9bc8c",
color2:"#8a6d1a", color3:"#1f1a12"}` (бежевый/тёмно-жёлтый/почти чёрный).

## Диалог классификации материалов (в самом Экспорт_JSON_3D.js)
`CollectMaterials` — уникальные базовые имена из `Material.MaterialName`
И `Plastics[].Material`, только выделенной модели; служебные (`~$$$...`,
"Габаритная рамка") отфильтрованы по имени объекта И по имени материала.

Две ветки окна (`USING_NEW_UI`):
- **Современный путь**: `UI.components.NewForm()` (НЕ легаси `NewForm()`
  — у легаси плашка заголовка рисуется СНИЗУ, платформенный баг,
  непочинибельный кодом). Виджеты вручную (Left/Top/Width/Height, без
  Align-системы). "Таблица" собирается вручную: `NewLabel`+
  `NewComboBox`+`NewColorComboBox`(`.EditValue`)+`NewCheckBox`(индикатор
  текстуры, disabled). Кнопки — `NewImageButton`. Персистентность своя:
  `fs.*` + `материалы_типы.json`.
- **Legacy-fallback** (старый Базис 2022, БОЛЬШИНСТВО пользователей):
  докнутая `Action.Properties`, `NewGroup`+`NewCombo`+`NewColor`(тут
  работает!)+`NewBool`. Персистентность штатная
  (`Action.Properties.Save/Load`).

Кодировка: старый Базис=CP1251, новый=UTF-8 → кириллица в строковых
литералах через `\uXXXX`-escape (общее правило проекта скриптов).

`TYPES_LIST` начинается с "Не задано" (индекс 0 = дефолт) — если стоит,
`MaterialCategory→null`, но `MaterialColorFallback` всё равно берётся.
`GetMaterialInfo` абстрагирует `.EditValue`(новый UI)/`.Value`(legacy).

Выборочный экспорт (`HasSelection`) должен фильтровать на ЛЮБОЙ глубине
вложенности блоков — см. `../CLAUDE.md`.

## Вьювер — сборка материала панели
`getMaterialConfig(el)`: `MaterialCategory` → lookup, фолбэк
`classifyMaterialByName`.
`getEffectiveMaterialConfig(el)`: то же, но `Plastics[0].Category`
побеждает (используется для решения "зеркалить ли").
`buildPanelMaterials(el,rgb,daeMaterials,textureMap,textureLoader,
thicknessM)` — ОБЩАЯ функция расчёта материалов (лицо-мин/лицо-макс/
торец), переиспользуется и в обычной геометрии, и в
`buildContourPanelMesh` (толщина считается по-разному в двух путях
геометрии, передаётся параметром). Возвращает `{faceMatMin,faceMatMax,
edgeMat,baseGuess}`. Plastics-per-side (`Side` 0→мин,1→макс) работает
одинаково в обоих путях геометрии.

## Процедурный шум торца (edge.mode="noise")
Общий тайл по толщине (не per-face). `getNoiseTexture(hex1,hex2,hex3,
aspectU=1,aspectV=1)`: низкое разрешение (`cellsPerThickness=40`) +
билинейное увеличение (крупные пятна), `color3` в тёмных местах (t<0.3,
после растяжения диапазона на полный контраст — без него box-blur
сжимает всё к середине). Возвращает `{map,bumpMap}` (bump=тёмное
физически ниже, `bumpScale=0.003`). `repeat=1/thicknessM`,
`MirroredRepeatWrapping`.

## Две плоскости среза (переработано 2026-08-14 — история версий ниже)
Во вьювере ДВЕ независимые кнопки-«разреза», обе теперь через ЧЕСТНУЮ
плоскость отсечения (`THREE.Plane` + `clippingPlanes` + настоящая
геометрия крышки сечения, не face-hiding и не трафаретный stencil):

- **`cutPlane`/"Разрез плоскостью"** — РУЧНАЯ, как было изначально:
  кнопка "Поставить плоскость среза" → клик по модели ставит плоскость
  в точке клика, нормалью на камеру; дальше стоит статично, пока не
  переставить заново или не подвинуть "Ближе"/"Дальше"/"Перевернуть
  сторону". Круглый визуальный индикатор (`cutVisualDisc`) — на месте.
- **`cutawayPlane`/"Разрез"** — ЖИВАЯ, всегда следует за камерой:
  центр = `controls.target` (текущий центр вращения — переставляется
  обычным кликом по объекту, отдельной "постановки" нет), нормаль =
  `camera.getWorldDirection()`, пересчитывается КАЖДЫЙ кадр в
  `updateCutawayFollow()` из главного цикла `animate()` (не по
  `controls.change` — не завязано на damping/окончание вращения). Без
  визуального индикатора и без "Ближе"/"Дальше"/"Перевернуть сторону" —
  не нужны при авто-следовании.

**Почему две отдельные плоскости, а не общий переключатель режима**:
`cutPlane` заходит в `clippingPlanes` КАЖДОГО материала всегда (и
`cutawayPlane` — тоже, оба сразу: `clippingPlanes:[cutPlane,
cutawayPlane]`), поэтому чтобы одна не резала сцену, пока её тумблер
выключен, её просто "паркуют" (`constant = PARK_CONSTANT = 1e9`, дальше
любых реальных размеров сцены) — `renderer.localClippingEnabled` стал
ОБЩИЙ на обе (`syncGlobalClipping()`, включён если активна хоть одна).
У каждой — своя группа крышек (`cutCapGroup`/`cutawayCapGroup`), свой
набор радиус-ограничивающих uniform'ов (см. ниже), своя копия
`addCutCap`/`applyRadiusDiscardToCapMaterial` (`addCutawayCap`/
`applyCutawayRadiusDiscardToCapMaterial` — не параметризовал общую
функцию ради одного доп. потребителя, дублирование сознательное).

**"Ручная" плоскость (`cutPlane`) технически не мутируется напрямую**:
авторитетное состояние (что реально "поставлено") живёт в `cutPlaneReal`
— `syncCutPlane()` копирует его в `cutPlane` (если `cutPlaneOn`) либо
паркует `cutPlane` (если выключено), не трогая `cutPlaneReal`. Нужно
именно для сосуществования с `cutawayPlane` — раньше, когда плоскость
среза была одна, для выкл/вкл хватало одного
`renderer.localClippingEnabled`.

Крышка (у обеих плоскостей) — честная геометрия сечения (не трафаретный
stencil-буфер, тот был раньше и переписан): `buildCutCapGeometryForMesh
(geo,plane)`, пересобирается в `rebuildCutCaps()`/`rebuildCutawayCaps()`
под каждую панель отдельно (клон `edgeMat` ЭТОЙ панели). Крышки —
отдельные группы прямо в `scene` (НЕ дети мешей — иначе портят bbox).
Радиус-ограничение крышки (квадрат `cutRadius=2.0`, чтобы не заливать
весь пол — круглый тест `distance()` ломал срез на практике, квадрат
надёжнее и дешевле) — общий приём, `onBeforeCompile`+`discard` в
фрагментном шейдере, как и у стенок тела выдавливания раньше (см. ниже).

**Важно**: `cutCapGroup.visible`/`cutawayCapGroup.visible` синхронизировать
везде, где меняется соответствующий тумблер.

### Старая "Разрез" (Sims cutaway) — заменена, история для контекста
До 2026-08-14 кнопка "Разрез" прятала грани по нормали к камере
(`decorNormals={min,max}` в `mesh.userData`, `material[1|2].visible=
false` на `controls.change`). **Проблема, из-за которой заменили**: у
тонкой панели (полка/дно) это прячет только ЕЁ СОБСТВЕННУЮ грань,
обращённую к камере — противоположная грань ТОЙ ЖЕ панели (в паре мм
ниже) не удовлетворяет тесту "смотрит на камеру" (её нормаль указывает
ровно в направлении взгляда, а не навстречу) и остаётся видна,
перекрывая вид "внутрь" — при взгляде сверху-вниз на полку видна была
только его собственная нижняя грань, загораживающая содержимое ниже.
Для СТЕН (вертикальных панелей анфас) технику это не портило — отсюда
и живучесть подхода. У стенок тела выдавливания (`el.IsExtrusion`) был
свой отдельный шейдер-дискард (`applyCutawayDiscardToWallMaterial`,
per-fragment, т.к. у замкнутого кольца стенок нет единого перед/зад) —
теперь не нужен, `cutawayPlane` режет их как всё остальное через
`clippingPlanes`.

Заодно раскопан отдельный **найденный разрыв (2026-08-14, до замены)**:
`el.IsExtrusion`, от которого зависел тот шейдер-дискард, отсутствовал
в JSON — не было кода, который его пишет, ни в одной из копий
`Экспорт_JSON_3D.js` на диске (только в старом тестовом
`viever/тест.json` от 6 августа) — та же картина, что и с
[[bazis-docs-vs-code-drift|анимацией]]. Восстановлено чтением нативного
`Obj.IsExtrusion` напрямую (try/catch, фолбэк `false`) — ГИПОТЕЗА, точное
имя поля не подтверждено дословно. Само поле `IsExtrusion` в экспортёре
ОСТАВЛЕНО (используется независимо для выбора UV-развёртки стенок —
периметр профиля vs кромка панели, см. `buildContourPanelMesh`), только
его cutaway-специфичный потребитель убран вместе со старой "Разрез".

## Кромка per-сторона из Obj.Butts — риск принят, код не собран
Подтверждено на одном примере: `ElemIndex=3` = задняя сторона без
кромки (Боковина, `Size=[300,2300,16]`). Остальные 3 индекса НЕ
подтверждены универсально для прямоугольных панелей (там `ElemIndex` не
имеет прямого сегмента контура для сверки, в отличие от контурных
панелей). Решено рискнуть — гипотеза "индекс 3 = задняя" как рабочее
правило. Собирать код — ждать отмашки пользователя.

## Panel.Cuts (пазы/фрезеровки) — экспортёр готов, декаль не размещена
`Line.Cuts=[{Name,Sign,TrajMin,TrajMax,ProfileWidth,ProfileHeight}]`.
Решение: паз рисуется ТЕКСТУРОЙ/декалью (не CSG), материалом торца без
кромки этой панели. `buildForcedOutline(geometry,color)` уже готова
(`userData.isForcedOutline`, не завязана на тумблер "Контур"), но пока
не используется. Координаты Trajectory, вероятно, решаются той же
формулой, что и Contour (см. `geometry.md`) — не проверено конкретно
для Cuts, стоит переиспользовать `frameMatrixFromCorners`-подход
напрямую при реализации.

## Отклонённая альтернатива
Тащить `.dae` внутрь скрипта экспорта JSON — движок Базиса слишком беден
для XML-парсинга, выигрыша в шагах нет.
